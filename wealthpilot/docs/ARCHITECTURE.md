# 系统架构与数据设计

## 1. 技术选择

采用 Node.js 24 内置 HTTP、SQLite、测试与加密模块，前端是原生 ES Modules。项目无需下载第三方依赖，适合快速启动、审查和离线演示。没有使用框架或云平台绑定，GitHub 只托管源码，部署需要支持 Node 和持久磁盘的主机。

这是有意识的单用户 MVP 设计：一个进程拥有一个工作台和一个 SQLite 数据库。它不是多租户系统，访问口令只保护该工作台的整体访问。

## 2. 模块边界

```text
浏览器（原生 HTML/CSS/JS）
    │ 同源 JSON 请求；Cookie 认证
    ▼
server.mjs：路由 → 来源校验 → 认证 → 频率/大小限制 → 输入校验
    ├── domain.mjs + strategies.mjs：风险/体检/策略对比/压力/目标/调仓
    ├── storage.mjs：SQLite 事务 → 工作台版本 + 审计 + 幂等结果
    └── evidence.mjs + advisor.mjs：主题资料与计算依据 → 规则/外部模型解释
```

前端渲染数据，不独立维护另一个金融计算实现。服务端不接受客户端传来的目标权重或最终交易金额；执行时用当前已存问卷和资产重新生成调仓计划。

## 3. 工作台数据

`workspace.body` 是 JSON，包含：

```json
{
  "profile": {
    "horizon": 5,
    "tolerance": 3,
    "experience": 2,
    "incomeStability": 3,
    "emergencyMonths": 6,
    "debtRate": 3,
    "monthlyExpense": 8000
  },
  "holdings": {"equity":132000,"bond":96000,"gold":24000,"cash":48000},
  "goal": {"name":"长期积累","target":600000,"years":5,"monthly":3000,"annualReturn":3,"inflation":2},
  "dataMode": "demo"
}
```

数据库中独立存储递增 `version`。1.1.0 还支持可选的 `strategy`（默认 policy）与 `holdingsUpdatedAt`（未知时为空）。手动修改资产将 `dataMode` 改为 `manual` 并记录核对时间；模拟调仓不刷新该时间，这仍然不是行情驱动的估值。金额保留到分，JavaScript 浮点中间计算最后舍入；更复杂的多币种交易系统应改为整型最小货币单位或定点十进制。

## 4. SQLite 表

| 表 | 字段 | 用途 |
|---|---|---|
| workspace | id=1, body, version | 单用户工作台当前快照 |
| audit | id, at, action, details | 问卷/资产/目标的 before/after，调仓明细和规则版本 |
| executions | key, response, fingerprint | 幂等结果缓存和请求指纹 |

启用 WAL 和 5 秒 busy timeout。首次启动创建 schema，存在旧的 `executions` 表时补齐 `fingerprint` 列。当前只有 schema 1；后续正式数据库升级需采用有序、可备份和可回滚的迁移，不能继续依靠零散补列。

审计记录不包含聊天内容或密钥。记录可由数据库管理者修改，因此不属于防篡改账本。接口展示最近 100 条，数据库保留全部；幂等结果没有自动过期，长时间使用需加入经过设计的保留策略。

## 5. 修改与调仓一致性

更新或执行启动 `BEGIN IMMEDIATE`：

1. 有幂等键时，读取已完成结果。请求指纹相同则返回原结果；不同则 409。
2. 读取当前工作台，检查客户端版本等于当前版本。
3. 执行受控更新；调仓由服务端重新计算。
4. 写入新快照与 `version + 1`。
5. 写入审计；调仓再保存幂等结果。
6. 提交；任一步出错则回滚。

因此旧标签页不能覆盖新数据，网络重试不能重复扣费。前端执行按钮在请求期间禁用；服务端机制仍然是最终保证。相同幂等键的重放返回原来执行时的快照，前端随后刷新最新工作台。

## 6. 认证、来源与部署

默认监听 `127.0.0.1`，无口令时只适用于个人可信设备。Host 必须为回环名称，变更请求必须有匹配的 Origin，服务不提供 CORS 跨域授权。

绑定非回环地址时要求至少 24 字符的 `ACCESS_TOKEN` 和明确的 `PUBLIC_ORIGIN`。登录使用 SHA-256 后的固定长度恒定时间比较；会话 ID 由安全随机数生成，Cookie 设 HttpOnly 和 SameSite=Strict，HTTPS 部署使用 Secure。会话有效期 8 小时，只保存在进程内，重启会退出所有会话。

写请求、登录和 AI 请求分别限流；请求体上限 32 KB。限流以 socket IP 为键，不信任任意转发头。反向代理后的所有用户可能共享一个限流键，这对单用户实例是可接受的限制。

访问令牌是单用户共享凭据，不是用户身份体系。不要为多用户业务复用这个架构。

## 7. AI 数据流

用户问题和同意开关 → 服务端读取最新组合 → 本地计算 → 构造最小上下文 → 可选外部模型 → 纯文本解释与固定来源集合。

配置不全或用户未同意时不调用外部服务。提供方必须为 HTTPS，禁止自动跟随重定向，20 秒超时。提供方错误信息不会原样暴露给浏览器，失败后标记降级。

本版从三份基础资料摘要中选择与问题相关的条目，将其与计算结果放入上下文。自动上下文增加目标期限、假设与资金达成比例，仍不发送绝对金额；具体金额只在浏览器计算依据中显示。**没有向量数据库、实时检索、训练、微调或逐句引用验证。** 提示词约束不是严格的安全防护，因此模型没有交易工具、文件权限或数据库写能力。

模型接口由服务端环境变量设定，不允许浏览器提供任意 URL。若未来允许用户配置提供方，需要额外加入网络出口限制、密钥管理和 SSRF 防护。

## 8. 前端状态与扩展接口

哈希导航对应八个工作页面；服务器只需提供根页面和固定静态文件。无客户端金融数据持久缓存，对话只在当前页面内存中保存。所有用户和模型字符串转义后渲染；不执行模型 HTML 或脚本。

若浏览器支持 `document.modelContext`，渐进注册只读 `read_wealth_analysis` 工具，读取与页面相同的分析。未支持的浏览器直接忽略。当前环境无可用 WebMCP 验证上下文，未验证该增强功能；核心页面和 API 不依赖它。

## 9. 未来扩展顺序

先引入用户/账户所有权与数据隔离，再加入价格主数据和估值流程，然后扩展交易约束与回测。任何真实执行模块都应独立于模型解释模块，具有订单状态机、资金检查、授权、幂等和对账；不应把大模型输出直接转成订单。
